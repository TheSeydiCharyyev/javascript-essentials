1. Не сейчас, а потом

До сих пор программа выполнялась сразу, сверху вниз, и всё, что ей нужно, было под рукой. Слушатели из дня 27 впервые сказали «сделай это потом — когда щёлкнут». Но щелчок — не единственное «потом». Бывает, что нужно подождать время или результат, который придёт не сразу.

ЗадачаЧем решаетсяДень
спрятать сообщение через 3 секундыsetTimeout30
обновлять часы каждую секундуsetInterval30
дождаться результата, который придёт позжепромис: then, catch30
получить данные с сервераfetch — он возвращает промис31

Главное правило дня: JavaScript не останавливается, чтобы подождать. Он записывает, что сделать потом, и сразу идёт дальше. Если бы страница замирала на каждое ожидание, она не отвечала бы ни на щелчки, ни на клавиши.

Два слова, которые встретятся на каждой странице MDN сегодня и завтра. Код, который выполняется сразу, строка за строкой, называют синхронным. Код, который выполнится потом, когда что-то случится, — асинхронным. Слушатели из дня 27, таймеры и промисы — всё это асинхронный код.

2. Учебная страница

Опыты сегодня — на странице секундомера. Кнопки заработают в разделе 6, поле заметки — в разделе 5, а с самого начала пригодятся часы и абзац для сообщений.

<!DOCTYPE html>
<html lang="ru">
<head>
  <meta charset="UTF-8">
  <title>Секундомер</title>
  <script src="app.js" defer></script>
</head>
<body>
  <h1>Секундомер</h1>
  <p id="clock">0.0</p>
  <button id="start">Старт</button>
  <button id="stop">Стоп</button>
  <button id="reset">Сброс</button>
  <p><input id="note" placeholder="Заметка"></p>
  <p id="message"></p>
</body>
</html>
const clock = document.querySelector("#clock");
const message = document.querySelector("#message");

// три готовые функции для опытов с промисами — как они устроены, в разделе 13
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
const later = (value, ms) => new Promise((resolve) => setTimeout(resolve, ms, value));
const failLater = (text, ms) => new Promise((resolve, reject) => {
  setTimeout(() => reject(new Error(text)), ms);
});

Три последние строки пока читать не нужно — это «чёрный ящик» для разделов 9–12. Так устроено большинство промисов в жизни: их возвращает чужая функция, а наша задача — правильно получить результат. Как сделать свой, разберём в конце.

3. setTimeout: сделать через время

setTimeout получает функцию и задержку в миллисекундах и вызывает функцию один раз, когда время выйдет. В секунде 1000 миллисекунд.

setTimeout(() => {
  message.textContent = "Прошло две секунды";
}, 2000);

Всё, что стоит после задержки, setTimeout передаст функции аргументами. Так можно отдать таймеру готовую функцию с параметром, не заворачивая её в стрелку:

function greet(name) {
  message.textContent = `Привет, ${name}!`;
}

setTimeout(greet, 1000, "Аман");   // через секунду: «Привет, Аман!»

Возвращает setTimeout номер таймера — обычное число. Результата функции он не возвращает и не может: функция ещё не выполнилась.

const id = setTimeout(greet, 1000, "Мерет");
typeof id;   // "number" — номер таймера, по нему таймер можно отменить

Скобки после имени

setTimeout(greet("Сапар"), 3000);
// «Привет, Сапар!» появилось сразу, а через три секунды — ничего

Со скобками greet("Сапар") выполнилась тут же, как любой вызов, и вернула undefined. Его и получил setTimeout вместо функции. Ошибки нет — просто через три секунды вызывать нечего. Таймеру отдают саму функцию: greet без скобок или стрелку () => greet("Сапар").

4. Код не ждёт

Что напечатает этот код и в каком порядке?

console.log("1: до");
setTimeout(() => console.log("3: таймер"), 1000);
console.log("2: после");
// 1: до
// 2: после
// 3: таймер — через секунду

setTimeout не ставит программу на паузу. Он записывает функцию «на потом» и сразу возвращается, поэтому «2: после» печатается раньше таймера. Пример с MDN делает это ещё нагляднее — три таймера, запущенные подряд:

setTimeout(() => console.log("первый"), 3000);
setTimeout(() => console.log("второй"), 2000);
setTimeout(() => console.log("третий"), 1000);
// третий
// второй
// первый

Порядок срабатывания решает время, а не порядок строк. И даже задержка 0 не значит «сейчас»: функция таймера подождёт, пока закончится весь текущий код.

Причина в том, что у страницы один поток выполнения: пока работает ваш код, браузер больше ничего не выполняет. Сработавший таймер становится в очередь и ждёт, когда поток освободится. Как устроена эта очередь, подробно разбирается в курсе 2; сегодня хватит правила «функция таймера — всегда после текущего кода».

setTimeout(() => console.log("таймер с задержкой 0"), 0);
console.log("обычный код");
// обычный код
// таймер с задержкой 0

5. clearTimeout: передумали

Номер из setTimeout нужен, чтобы отменить таймер, пока он не сработал:

const reminder = setTimeout(() => {
  message.textContent = "Пора отдохнуть!";
}, 5000);

clearTimeout(reminder);   // через 5 секунд ничего не случится

Отмена уже сработавшего таймера или чужого номера ничего не делает и ошибки не даёт. clearTimeout(undefined) — тоже. Это пригодится прямо сейчас.

Сообщение на три секунды

Частая задача: показать «Сохранено» и через три секунды убрать. Первая версия:

function flash(text) {
  message.textContent = text;
  setTimeout(() => {
    message.textContent = "";
  }, 3000);
}

Вызовем её дважды с перерывом в две секунды: flash("Сохранено"), а потом flash("Удалено"). «Удалено» исчезнет уже через секунду, а не через три.

Шаг 1. Кто стёр сообщение? Таймер. Но таймер второго вызова должен сработать только на пятой секунде, а стерло на третьей.

Шаг 2. Сколько таймеров? Два. Первый вызов тоже оставил таймер, и он ничего не знает о втором сообщении: на третьей секунде он честно стёр то, что было в абзаце, — уже «Удалено».

Шаг 3. Чиним. Новое сообщение отменяет старый таймер. Для этого номер таймера хранят в переменной снаружи функции — чтобы следующий вызов его увидел:

let flashTimer;

function flash(text) {
  clearTimeout(flashTimer);         // прежний таймер больше не нужен
  message.textContent = text;
  flashTimer = setTimeout(() => {
    message.textContent = "";
  }, 3000);
}

При первом вызове flashTimer ещё undefined, и clearTimeout молча ничего не делает. Теперь «Удалено» держится полные три секунды: до пятой.

Подождать, пока допечатают

Тот же приём — «новое событие отменяет старый таймер» — даёт автосохранение. Сохранять на каждую букву незачем; сохраним, когда человек перестал печатать хотя бы на секунду:

const note = document.querySelector("#note");
let saveTimer;

note.addEventListener("input", () => {
  clearTimeout(saveTimer);                  // печатает дальше — отложить
  saveTimer = setTimeout(() => {
    flash(`Сохранено: ${note.value}`);
  }, 1000);
});
// набрали «Купить хлеб» без пауз: через секунду — одно сообщение «Сохранено: Купить хлеб»

Каждая буква — событие input из дня 28, и каждое отменяет таймер прошлой буквы. Сработает только таймер последней. Сделайте паузу посреди слова — сообщений будет два. Так же работает поиск, который ждёт, пока вы допечатаете запрос: на дне 32 он понадобится в каталоге, чтобы не спрашивать сервер на каждую букву.

6. setInterval: секундомер

setInterval похож на setTimeout, но вызывает функцию снова и снова через равные промежутки, пока её не остановят через clearInterval. Этого хватает для секундомера:

let tenths = 0;        // прошло десятых долей секунды
let timerId = null;    // номер интервала; null — секундомер стоит

function tick() {
  tenths++;
  clock.textContent = (tenths / 10).toFixed(1);
}

document.querySelector("#start").addEventListener("click", () => {
  timerId = setInterval(tick, 100);
});

document.querySelector("#stop").addEventListener("click", () => {
  clearInterval(timerId);
});

document.querySelector("#reset").addEventListener("click", () => {
  tenths = 0;
  clock.textContent = "0.0";
});

Каждые 100 миллисекунд tick прибавляет десятую долю и показывает время: toFixed(1) из дня 17 держит один знак после точки. Нажали «Старт», подождали три секунды — на часах 3.0. «Стоп» останавливает счёт, «Сброс» обнуляет.

Проверим в консоли, что «Стоп» сделал с переменной:

// нажали «Старт», через секунду «Стоп»:
clock.textContent;   // "1.0"
timerId !== null;    // true — счёт остановлен, а номер в переменной остался

clearInterval останавливает интервал, но переменную не трогает: в ней по-прежнему старый номер. Запомните это — в следующем разделе пригодится.

Секундомер считает щелчки таймера, а не настоящее время, — и это упрощение. Как увидим в разделе 8, таймер может опоздать. Точные часы сверяются с Date.now() из дня 17; это одно из заданий.

7. Разбор: «Старт» нажали дважды

Запустите секундомер и нажмите «Старт» ещё раз. Через секунду на часах 2.0: время побежало вдвое быстрее. Нажмите «Стоп» — часы не остановились, а пошли с обычной скоростью.

Шаг 1. Почему вдвое быстрее? Каждый щелчок по «Старт» запустил свой интервал. Теперь tick зовут два интервала, и за секунду она срабатывает 20 раз вместо 10.

Шаг 2. Почему «Стоп» не помог? В timerId лежит только последний номер: второй щелчок записал свой номер поверх первого. «Стоп» остановил второй интервал, а номер первого потерян навсегда — остановить его больше нечем.

Шаг 3. Чиним. Не запускать второй интервал, пока идёт первый, и после остановки отмечать, что секундомер стоит:

document.querySelector("#start").addEventListener("click", () => {
  if (timerId !== null) return;     // уже идёт — второй не запускаем
  timerId = setInterval(tick, 100);
});

document.querySelector("#stop").addEventListener("click", () => {
  clearInterval(timerId);
  timerId = null;                   // стоит — «Старт» снова работает
});

Правило на все таймеры: номер таймера — такие же данные, как всё остальное. Потерянный номер — таймер, которым больше никто не управляет.

8. Задержка — «не раньше чем»

Задержка в setTimeout — это «не раньше чем», а не «ровно через». Функция таймера ждёт, пока браузер освободится. Займём его на секунду:

const start = Date.now();
setTimeout(() => console.log(`прошло ${Date.now() - start} мс`), 100);
while (Date.now() - start < 1000) {}   // браузер занят целую секунду
// прошло 1000 мс — хотя просили 100

Пока крутится цикл, страница не отвечает ни на что: ни таймеры, ни щелчки не выполняются. Долгие вычисления замораживают страницу целиком — вот почему JavaScript никогда не ждёт «стоя»: ожидание через таймер не мешает остальному.

СлучайЧто будетПочему
задержка 0после всего текущего кодатаймер ждёт, пока код закончится
setTimeout(f, 0), вызванный из таймера, и так много разпосле пяти вложенных — не меньше 4 мстак велит стандарт HTML
задержка "1 second"сработает сразустрока стала NaN, а NaN — 0
задержка больше 2147483647 мс2 ** 32 - 5000 срабатывает сразучисло хранится в 32 битах и переполняется
clearTimeout для setIntervalтоже останавливаетномера у них общие, но лучше не путать

Если работа внутри интервала может длиться дольше самого интервала, MDN советует цепочку из setTimeout: каждый следующий вызов планируется только после того, как закончился предыдущий.

function tickLater() {
  tick();
  timerId = setTimeout(tickLater, 100);   // следующий — когда этот закончился
}

9. Промис — обещание результата

Таймер отвечает на вопрос «когда». Но часто нужно другое: получить результат, которого ещё нет, — данные с сервера, ответ на запрос. Для этого в языке есть промис (от английского promise — обещание): объект, который обещает результат потом.

У промиса три состояния. Сначала он ждёт (pending). Потом — один раз и навсегда — либо выполняется со значением (fulfilled), либо отклоняется с ошибкой (rejected). Выполненный или отклонённый промис называют завершённым (settled). Консоль Chrome показывает состояние прямо в выводе:

const p = wait(1000);
p;   // Promise {<pending>}
// через секунду:
p;   // Promise {<fulfilled>: undefined}

wait обещает только «время прошло», поэтому значение — undefined. later обещает значение, а failLater — ошибку:

later("Аман", 500);           // через полсекунды: Promise {<fulfilled>: 'Аман'}
failLater("Нет связи", 500);  // через полсекунды: Promise {<rejected>: Error: Нет связи}
// Uncaught (in promise) Error: Нет связи

Последняя строка — красная: у отклонённого промиса никто не обработал ошибку. Чем её поймать — раздел 11.

10. then: получить результат

Значение из промиса напрямую не достать: его ещё нет. Вместо этого промису отдают функцию — «когда будет готово, вызови её с результатом». Это then:

later("5 4 9", 1000).then((text) => {
  console.log(`пришло: ${text}`);
});
// через секунду: пришло: 5 4 9

Главная особенность then: он возвращает новый промис — с тем значением, которое вернула функция. Поэтому then можно ставить цепочкой, и каждый шаг получает результат предыдущего:

later("5 4 9", 1000)
  .then((text) => [...text].filter((ch) => ch !== " "))   // ["5", "4", "9"]
  .then((marks) => marks.map(Number))                     // [5, 4, 9]
  .then((marks) => console.log(Math.max(...marks)));      // через секунду: 9

Это parseMarks из «Табеля» на дне 28, только разложенный на шаги. Каждый шаг — короткая функция: получила значение, вернула новое. Что then вернул новый промис, легко проверить:

const first = later(2, 100);
const second = first.then((x) => x * 10);
first === second;   // false — это разные промисы
// через 100 мс: second — Promise {<fulfilled>: 20}

А если шаг сам возвращает промис, цепочка дождётся его и передаст дальше уже значение. Так одно ожидание идёт за другим:

later("Аман", 1000)
  .then((name) => later(`${name}: 4.33`, 1000))   // ещё секунда ожидания
  .then((line) => console.log(line));             // через 2 секунды: Аман: 4.33

Все случаи сразу — по странице MDN о then:

Функция шага…Следующий then получит
вернула значениеэто значение
ничего не вернулаundefined — сразу (раздел 14)
вернула промисего значение, когда он выполнится
бросила ошибкуничего: ошибка уйдёт к catch (раздел 11)

Лесенка вместо цепочки

Зачем всё это, если есть таймеры? Попробуйте сделать три шага по секунде одними таймерами. Каждый следующий придётся вложить в предыдущий:

setTimeout(() => {
  console.log("шаг 1");
  setTimeout(() => {
    console.log("шаг 2");
    setTimeout(() => console.log("шаг 3"), 1000);
  }, 1000);
}, 1000);

Код уезжает вправо лесенкой, и чем больше шагов, тем хуже: MDN называет это «адом обратных вызовов». С промисами шаги стоят друг под другом:

wait(1000)
  .then(() => { console.log("шаг 1"); return wait(1000); })
  .then(() => { console.log("шаг 2"); return wait(1000); })
  .then(() => console.log("шаг 3"));
// шаг 1, шаг 2, шаг 3 — с интервалом в секунду, как и лесенка

11. catch: поймать ошибку

Если промис отклонён, функции в then не вызываются. Ошибка идёт по цепочке вниз до первого catch:

failLater("Сервер не ответил", 1000)
  .then(() => console.log("это не выполнится"))
  .catch((err) => console.log(`Ошибка: ${err.message}`));
// через секунду: Ошибка: Сервер не ответил

Отклонить промис может не только тот, кто его создал. Если функция внутри then бросает ошибку — через throw из дня 11 или сама, как JSON.parse на кривой строке, — новый промис отклоняется, и ошибка тоже уходит в catch:

later('[5, 4', 500)
  .then((text) => JSON.parse(text))        // строка оборвана — JSON.parse бросает
  .then((marks) => console.log(marks))     // пропущен
  .catch((err) => console.log(err.name));  // через полсекунды: SyntaxError

Один catch в конце ловит ошибку любого шага выше — как один try...catch вокруг нескольких строк. А после catch цепочка может продолжиться: что вернул catch, то и получит следующий then.

failLater("Нет связи", 500)
  .catch(() => [])                              // вместо ошибки — пустой список
  .then((list) => console.log(list.length));    // через полсекунды: 0

Кстати, catch(f) — это краткая запись then(undefined, f): у then есть и второй параметр, функция для ошибки. Но цепочка с catch в конце читается проще, и MDN советует именно её.

12. finally: в любом исходе

Иногда что-то нужно сделать, чем бы ни кончилось: убрать «Загрузка…», снова включить кнопку. Писать это и в then, и в catch — повторение. Для этого есть finally:

message.textContent = "Загрузка…";
later("Готово", 1000)
  .then((text) => console.log(text))
  .catch((err) => console.log(err.message))
  .finally(() => {
    message.textContent = "";               // и после успеха, и после ошибки
  });

Функция в finally не получает аргументов: ей не важно, чем кончилось. И значение она пропускает дальше, не меняя:

Promise.resolve(2).finally(() => 77);   // Promise {<fulfilled>: 2}

Есть одно исключение: если в finally случится ошибка, цепочка всё-таки отклонится с ней, и следующий catch получит уже её. Поэтому в finally кладут только простую уборку — спрятать, показать, включить.

13. Свой промис: new Promise

Пора открыть «чёрный ящик» из раздела 2. Промис создают конструктором new Promise и передают ему функцию-исполнитель. Исполнитель получает две функции: resolve — выполнить промис со значением и reject — отклонить с ошибкой.

const coin = new Promise((resolve, reject) => {
  setTimeout(() => resolve("орёл"), 1000);
});

coin.then((side) => console.log(side));   // через секунду: орёл

Три правила исполнителя, каждое проверено в консоли.

Исполнитель запускается сразу, в момент new. Ждёт не он, а функции в then:

console.log("до");
new Promise((resolve) => {
  console.log("исполнитель");
  resolve("готово");
}).then((value) => console.log(value));
console.log("после");
// до
// исполнитель
// после
// готово

Считается только первый вызов. Промис завершается один раз, остальные resolve и reject молча пропадают:

new Promise((resolve, reject) => {
  resolve("первый");
  resolve("второй");
  reject(new Error("поздно"));
});
// Promise {<fulfilled>: 'первый'}

Ошибка в исполнителе отклоняет промис — но только если она брошена сразу. Ошибку, брошенную позже, внутри таймера, промис уже не увидит: она станет обычной необработанной ошибкой, а промис навсегда останется в ожидании. Поэтому из таймера зовут reject, а не бросают throw.

new Promise(() => {
  setTimeout(() => {
    throw new Error("Из таймера");          // catch этого не поймает
  }, 100);
}).catch((err) => console.log("поймали"));
// Uncaught Error: Из таймера — а «поймали» так и не напечатано

Теперь понятно, как устроены помощники со страницы. Каждый — старый добрый setTimeout, завёрнутый в промис. MDN называет это главным поводом писать new Promise: обернуть старый способ «через функцию» в промис.

// строка из app.js (раздел 2) — в консоли её не набирайте: wait уже объявлена
const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
// setTimeout вызовет resolve через ms миллисекунд — промис выполнится

Готовый промис: Promise.resolve и Promise.reject

Когда значение уже есть, а нужен промис, пишут коротко: Promise.resolve(42) — сразу выполненный, Promise.reject(new Error("…")) — сразу отклонённый. Но даже у готового промиса функция в then вызывается не сразу, а после текущего кода. MDN называет это гарантией: then никогда не срабатывает посреди вашего кода.

Promise.resolve("потом").then((value) => console.log(value));
console.log("сейчас");
// сейчас
// потом

14. Разбор: забыли return

Цепочка из раздела 10, но шаг записан с фигурными скобками:

later("Аман", 500)
  .then((name) => {
    later(`${name}: 4.33`, 500);            // return забыли
  })
  .then((line) => console.log(line));
// через полсекунды: undefined

Шаг 1. Что не так? Два симптома: вместо «Аман: 4.33» — undefined, и напечатано через полсекунды, а не через секунду.

Шаг 2. Почему? Со скобками стрелка возвращает только то, что после return (день 13). Без него шаг вернул undefined, новый промис выполнился с ним сразу, и следующий then не стал ждать. Второй промис later создан, но с цепочкой не связан — MDN называет такой «плавающим».

Шаг 3. Чиним. return later(…) или стрелка без скобок, как в разделе 10. Правило MDN: если в шаге появился промис — верните его.

Вторая частая ошибка — цепочка без catch. Пока всё хорошо, её не видно. Но стоит промису отклониться, в консоли появится красное Uncaught (in promise), а программа молча не сделает того, что должна. Любая цепочка кончается catch.

15. «Табель» загружается

На дне 23 данные «Табеля» пришли строкой JSON «как из файла или с сервера». Но с сервера данные не приходят мгновенно. Сделаем честно: строка придёт через секунду, а пока — надпись «Загрузка…». На страницу, между таблицей и итогом, добавляется абзац:

<p id="loading">Загрузка…</p>
// без изменений: расчёт, makeCells, классы, makeRow, addDeleteButton, updateSummary,
// слушатели tbody и Esc (дни 23–27), форма (день 28)
// убраны: const students = JSON.parse(saved) (день 23)
// и const reports = …, tbody.append(…), updateSummary() (день 27)

// новое: данные приходят через секунду — так, как придут с сервера
function loadSaved() {
  return new Promise((resolve) => {
    setTimeout(resolve, 1000, saved);
  });
}

const reports = [];   // пусто, пока данные не пришли
const loading = document.querySelector("#loading");

loadSaved()
  .then((text) => JSON.parse(text))
  .then((students) => {
    const loaded = students.map(makeReport);
    reports.push(...loaded);
    tbody.append(...loaded.map(makeRow).map(addDeleteButton));
    updateSummary();
  })
  .catch((err) => {
    document.querySelector("#summary").textContent = `Не удалось загрузить: ${err.message}`;
  })
  .finally(() => {
    loading.hidden = true;
  });

Каждый шаг цепочки — знакомая работа: разобрать строку, посчитать отчёты, построить строки, подвести итог. Новое только в том, когда она делается. А reports остался const: массив заполняется через push, и удаление и форма со дней 27–28 работают с ним как раньше.

Разбор: студента добавили во время загрузки

Появилась новая ошибка, которой раньше быть не могло. Пока висит «Загрузка…», форма уже работает. Добавим за эту секунду «Аман» с оценками «5 5»:

Что сделалиЧто на странице
«Аман», «5 5» во время загрузкистрока «Аман 5.00», проверка повтора не сработала: reports ещё пуст
данные пришлишесть строк, два «Амана», «Отличников: 3 из 6»
«Удалить» у второго «Амана», OKисчезла вторая строка, а из данных удалён первый «Аман»: на странице три отличника, в итоге — «Отличников: 2 из 5»

Шаг 1. Что сломалось? Страница и данные разошлись: удаление ищет студента по имени, а имён «Аман» два — ровно то, от чего защищала проверка повтора на дне 28.

Шаг 2. Почему проверка пропустила? Она сравнивала с reports, а тот был пуст: данные ещё в пути. Проверка верна для готовых данных, а форма разрешила действовать раньше, чем они пришли.

Шаг 3. Чиним. Пока данных нет, форма не нужна. Прячем её до загрузки и показываем в finally:

form.hidden = true;                 // новое: до загрузки добавлять рано

loadSaved()
  // … then и catch без изменений
  .finally(() => {
    loading.hidden = true;
    form.hidden = false;            // новое
  });

Это общее правило всего, что приходит «потом»: пока результата нет, программа не должна делать вид, что он есть. Надпись «Загрузка…», спрятанная форма, выключенная кнопка — всё это способы честно сказать «подождите».

Что будет завтра

На дне 31 появится fetch — запрос к серверу. Он возвращает промис, и всё сегодняшнее — then, catch, finally — работает с ним без изменений. Там же будет async и await: другая запись тех же промисов, которая читается как обычный код сверху вниз.   // из таймера — reject(new Error("…")), не throw

Promise.resolve(42);   Promise.reject(new Error("…"));
  1. В каком порядке напечатаются строки: console.log("А"), setTimeout(() => console.log("Б"), 0), console.log("В")?
    Ответ А, В, Б. Функция таймера ждёт, пока закончится текущий код, даже с задержкой 0.
  2. Почему setTimeout(greet("Сапар"), 3000) показывает приветствие сразу?
    Ответ Скобки вызывают функцию тут же, и таймер получает её результат — undefined. Таймеру отдают саму функцию, без скобок.
  3. Секундомер ускорился после второго нажатия «Старт». Что произошло и как это предотвратить?
    Ответ Запустились два интервала, а номер первого затёрт вторым. Перед запуском проверять timerId !== null, после остановки писать timerId = null.
  4. Что вернёт then, и почему это позволяет строить цепочки?
    Ответ Новый промис со значением, которое вернула функция шага. Следующий then вешается уже на него и получает это значение.
  5. В середине цепочки JSON.parse бросил ошибку. Что будет с остальными then?
    Ответ Они пропускаются, ошибка уходит к ближайшему catch. Без catch в консоли будет Uncaught (in promise).
  6. Почему из таймера внутри исполнителя зовут reject, а не throw?
    Ответ Исполнитель к тому времени уже закончился: ошибку из таймера промис не увидит, она станет необработанной, а промис останется в ожидании навсегда.
