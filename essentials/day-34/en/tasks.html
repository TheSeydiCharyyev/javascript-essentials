Day 34. Tasks

Lessons 2 and 3, 90 minutes. Warm-up — 20 minutes, main tasks — 50 minutes, starred tasks — 20 minutes. The warm-up is on the example of the “Cards”: copy the folder day-33/cards to day-34/cards and finish it by the lecture. The main tasks are in your own project (day-33/project), by your own plan. After every task — a check and a note of the minutes in plan.md. We open everything through Live Server.

Warm-up

1. The current card and flipping
Easy6 min

do the first task of the plan by the steps of the lecture.

Add the function current from section 3, the new render and the listener of flipping from section 4.

The listener only changes flipped; what to show — the word or the translation — is decided by render.
  • a click on the card — “kitap”, one more click — “book”;
  • with learned of all eight numbers current() is null;
  • the listener is rewritten for a while as flipped = true — it is written down what broke;
  • the task and the real minutes are marked in the plan.
2. “I know” and “Again”
Easy7 min

go around the deck in a circle and not lose a single word.

Add both listeners from sections 5–6 and the check function testCurrent.

The remainder of division lives in current, not in the listener: “Again” simply adds one.
  • testCurrent() and testDeck() are silent;
  • “Again” eight times — “book” again, position is 8;
  • “Again” seven times, then “I know” at “window” — “book” again;
  • after a dozen mixed clicks the check for repeats in learned gives 0.
3. Topics, saving, an empty deck
Easy7 min

finish the example and go through the feature table.

Add the topic buttons, writing to storage, the empty deck and “Start over” from sections 9–11. Go through the scenario of section 15 in full.

  • all the rows of the scenario of section 15 matched;
  • the topic “home”, “I know” twice — “All the words of this topic are learned!”, no buttons;
  • “Start over” with Cancel changes nothing, with OK — “Learned: 0 of 8”;
  • the program is compared with section 14 — there are no differences.

Main tasks

4. The first task of your plan
Medium12 min

start the implementation with the task the others rely on.

Take the first task of day 34 in your project. If several listeners talk about the same thing — the selected item, the current question, the chosen category — first move it into a function, like current.

A function that only answers and changes nothing is easy to check in the console. Let it return “there is nothing” as null instead of failing.
  • the task is checked the way it is written in the plan — by hand and in the console;
  • the new function is checked in the console on at least two values, one of them “empty”;
  • a copy of the project folder is made before the edit;
  • the task and the real minutes are marked in the plan.
5. The next tasks and a guard
Medium13 min

move by the plan and not break what is done.

Do the next tasks of the plan one at a time. For the main function of your project create a check function in the spirit of testCurrent — it changes the data for a while and puts it back.

A good check fails on a stub and is silent on the real code. Run it after every task — even one that “has nothing to do with it”.
  • every closed task has a mark and minutes in the plan;
  • the check function is silent, and after it is called the data is the same as before;
  • at least once the check caught a breakage you did not notice by eye — or it is written down why there were none;
  • in the listeners that change “the current one”, the dependent variables are reset.
6. The empty state
Medium12 min

make “there is nothing” look as intended.

Find all the places in your project where something can turn out empty: an empty list, nothing found, everything done. For each one — a clear text, useless buttons hidden and a guard in the listeners.

The rule of section 12: the button is hidden, and the listener is still guarded with the first line if (… === null) return;.
  • all the empty states of the project are written out, for each one — how to reach it;
  • each one has a clear text instead of emptiness;
  • calling a listener from the console (button.click()) in the empty state gives no red lines;
  • rows about the empty states are added to the feature table.
7. Saving and checking by the table
Medium13 min

make sure that what was promised works in full.

If your project has something to remember — writing at the end of render, reading at the declaration. Then go through your feature table row by row, as at the defense, and mark each one: works, works with a reservation, not done.

Reset the data, not the storage: render will rewrite the key by itself — the walkthrough of section 13.
  • after a reload of the page what was saved is in place;
  • the reset — if there is one — erases the data, and after a reload it does not come back;
  • every row of the table has a mark, and a “with a reservation” row has the reservation itself;
  • everything “not done” is moved to the plan of day 35 or to “later”.

Starred tasks

8. Three complaints about the “Cards”
Hard10 min

look for a mistake by its symptom.

A classmate built the “Cards” and sent three complaints:

  • “After the eighth ‘Again’ the card gets stuck, and there is red in the console.”
  • “I pressed ‘I know’ on a flipped card — the next one showed the translation at once.”
  • “‘Start over’ resets nothing, even after a reload.”

Their code differs from the program of section 14 in three places:

// in current
return cards.length === 0 ? null : cards[position];

// in the “I know” listener — one line is missing
learned.push(current().id);
render();

// in the “Start over” listener
localStorage.removeItem(KEY);
For each complaint ask the data: position, flipped, learned and storage.
  • each complaint is reproduced in a copy of the “Cards” and matched with its place;
  • for the first one the exact text of the error from the console is written down;
  • for the third one it is written down what is in learned and in storage after “Start over”;
  • all three places are fixed, the complaints do not repeat.
9. Plan and actual
Hard10 min

compare the estimate with the real work and calmly recount tomorrow.

Add the real minutes to the tasks of your day 34 as an array actual, as in section 16, and compute the overrun with code. Recount day 35: if it does not fit — decide what moves to “later”. New ideas that came today go to “later”, with minutes.

  • for every task — the plan and the actual time, the sum is computed with code;
  • for the task with the biggest overrun it is written down where the time went;
  • day 35 without the “later” tasks fits into 90 minutes;
  • it is explained why exactly this task was chosen to be thrown out.
